## 5. Gate 验证（**进入 Phase 3A 开发前必须完成**）

### G2 — `fatigue` 方向（**最高优先，1 分钟**）

| 步 | 操作 | 记录 |
|---|---|---|
| 1 | 静止站立 3 秒 | `fatigue` 值、原生面板对应条的位置 |
| 2 | 连续冲刺 10 秒 | `fatigue` 升还是降？ |
| 3 | 连续挥砍 10 次 | 同上 |
| 4 | 喝「耐力药剂 / Stamina Potion」（buff 28，实测 `energyPerSecond=+3`） | 哪个字段变化？**若只有 energy 变、fatigue 不变 → 证实 stamina=energy** |
| 5 | 建造一件物品（消耗 ENERGY 活力） | `energy` 是否下降？ |

**判定**：
- 若冲刺/挥砍使 `fatigue` **下降** → fatigue 是"可消耗资源"（越高越好）；
- 若使 `fatigue` **上升** → fatigue 是"疲劳累积"（越高越糟）；
- 若 `fatigue` 完全不动、只有 `energy` 动 → fatigue 需另找触发条件（可能只与睡眠相关），
  此时 3A 的 Fatigue 项应**直接取消**。

### G3 — `AddBuff` 第二参数语义（**5 分钟**）

| 步 | 操作 | 期望 |
|---|---|---|
| 1 | 临时调试命令：`AddBuff(11, 5)` | 若 buff 立刻消失 → 第二参数是**绝对结束时间** |
| 2 | `AddBuff(11, Time.time + 5)` | buff 持续约 5 秒 → 证实绝对时间语义 |

### G1 — setter 生效且不破坏状态（**10 分钟**）

| 步 | 操作 | 期望 |
|---|---|---|
| 1 | `hp = maxHP - 1` | 血条立即反映；无异常日志 |
| 2 | 再受一次小伤害 | 正常掉血、受击动画正常 |
| 3 | 存档 → 读档 | 数值保持（验证是否写入存档） |
| 4 | `energy = maxEnergy` | 对应 UI 条刷新 |

**注意**：G1 是唯一"故意改玩家数值"的验证，必须在**独立测试存档**里做，并在结束后
读档或改回，避免污染正常进度。

### G4 — `energy` / `fatigue` 对应哪根 UI 条（**含在 L2**）

原生面板有 `hpBar / energyBar / apBar / fatigueBar / hungerBar / thirstBar`（A 级签名），
需目视确认哪根条对应哪个字段。`apBar` 的语义尚未映射到任何已知字段（**D：未找到**），
Phase 3 不处理 AP。

## 9. 环境限制与替代方案

**当前限制**：自动化会话无法进入存档（游戏 UI 按 2560×1600 布局，桌面 1463×914，菜单在屏幕外；
已用"移除本模组"隔离实验排除本模组原因）。

**替代方案（按优先级）**：

1. **由用户在可正常进游戏的会话里执行 G1/G2/G4/G5/G6**（每项都是分钟级）；
2. 若希望自动化：把游戏分辨率改为与桌面一致（窗口化），再进行；
   —— 本项目不再尝试自动改注册表分辨率（Phase 2 实测被游戏强制覆盖，且已还原原值）；
3. 只读部分（L1）可继续在自动化会话里跑，不需要存档。
